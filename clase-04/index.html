De tu compu a internet: hosting, dominios y riesgos

Armaste algo con Claude, ¿y ahora? Cómo pasar de tenerlo corriendo en tu computadora a que cualquiera lo pueda abrir con un link, qué significan host y dominio, cómo publicar gratis, y los riesgos que hay que cuidar antes de hacerlo público.

devices Antes de publicar nada

Las formas de usar una app hecha con Claude

No todo tiene que terminar con una URL pública. Depende de quién la necesita usar, y cuándo.

computer
Gratis · sin deploy

Local

corre en tu computadora

Vive y se ejecuta solo en tu máquina. Nadie más la puede abrir salvo que esté sentado enfrente tuyo (o en tu misma red).

Ideal para: probar una idea, una herramienta de uso personal, o algo que solo necesitás vos por ahora.
auto_awesome
Gratis · cero config

Artifact / preview de Claude

Claude la hostea por vos

Claude publica la página y te da una URL al toque, sin que tengas que elegir hosting ni configurar nada. Esta misma web del taller nació así.

Ideal para: compartir algo rápido con el equipo. Ojo: no controlás el dominio ni el hosting real por detrás.
cloud
Requiere deploy

Hosteada

vive en un servidor, 24/7

La subís a un servicio de hosting (gratis o pago) y queda corriendo todo el tiempo, con su propia URL pública y, si querés, un dominio propio.

Ideal para: algo que necesita estar siempre disponible para otras personas, no solo para vos.
dns Los dos términos que se confunden

Qué es un host, qué es un dominio

Se usan casi como sinónimos pero son cosas distintas, y contratás cada uno por separado.

dns

Host (hosting)

dónde vive tu app

Es el servidor que corre tu app las 24 horas y la entrega a quien la pida. Sin host, tu app solo existe mientras tu compu esté prendida y conectada a internet.

Ejemplo: Vercel, Netlify o Railway son servicios de hosting.
language

Dominio

cómo la encuentran

Es la dirección fácil de recordar (kidscorp.digital) que apunta a tu host, en vez de tener que escribir una serie de números (la IP). Se alquila por año, no se compra para siempre.

Ejemplo: podés usar la URL gratis que te da el hosting (tuproyecto.vercel.app) o comprar tu propio dominio y apuntarlo ahí.

Una forma simple de pensarlo: el host es la casa donde vive tu app, el dominio es la dirección postal para que la gente la encuentre. Podés vivir sin cartel con tu nombre (la URL gratis del hosting), o comprar un cartel propio (un dominio) y ponerlo en la puerta de esa misma casa.

rocket_launch Opciones gratuitas

Publicar gratis: Vercel y alternativas

Vercel es la más usada para proyectos como los que arma Claude Code, pero no es la única: Netlify, GitHub Pages y Railway cubren casos parecidos, todas con un plan gratuito que alcanza para un proyecto interno o un prototipo.

1

Subís tu proyecto a GitHub

Un repositorio, aunque sea privado. Es el punto de partida que Vercel va a leer.

2

Entrás a Vercel con tu cuenta de GitHub

Gratis, sin tarjeta. Le das permiso para ver tus repositorios.

3

Elegís el repositorio

Vercel detecta automáticamente qué tipo de proyecto es y lo configura solo, sin que tengas que tocar nada técnico.

4

Le das "Deploy"

En un par de minutos te da una URL pública (tuproyecto.vercel.app) que ya podés compartir.

5

(Opcional) Conectás un dominio propio

Desde la configuración del proyecto, apuntás tu dominio comprado a esa misma app.

Después del primer deploy, se actualiza sola: cada vez que subís un cambio a GitHub, Vercel vuelve a publicar automáticamente. No hace falta repetir el proceso a mano.

Riesgos de hacer algo visible online

Publicar es fácil; publicar sin cuidar esto es lo que sale caro o expone datos que no debían salir.

key_off

API key expuesta en el frontend

Si tu API key queda escrita en el código que corre en el navegador, cualquiera que abra "Ver código fuente" la puede copiar y usarla a tu costa.

Solución: las keys van del lado del servidor. Si tu app necesita usar una API paga, un backend intermedio la llama por vos, nunca el navegador directo.
trending_up

Sin límites de uso

Una API pública sin límite de pedidos puede recibir miles de llamadas (por error o a propósito) y generarte una factura enorme, o directamente tirar el servicio.

Solución: poné límites de uso (rate limiting) y alertas de gasto desde el primer día.
folder_off

Datos sensibles en un repo público

Contraseñas, claves o datos de usuarios pegados directo en el código, y ese repositorio queda visible para cualquiera en internet.

Solución: usá variables de entorno para cualquier dato sensible, y nunca las subas al repositorio.
shield

Permisos mal configurados

Dejar que cualquier sitio o cualquier persona pueda leer o modificar datos que deberían ser solo tuyos o de tu equipo.

Solución: restringí accesos (CORS, autenticación) a lo mínimo que tu app realmente necesita.

La regla que resuelve casi todo: nada sensible (keys, contraseñas, datos de gente) vive en el código que le llega al navegador del usuario. Si tenés dudas sobre si algo es "seguro" de mostrar, asumí que no lo es y ponelo del lado del servidor.
